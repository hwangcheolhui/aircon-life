## 0. 한 줄 요약

**TypeScript 모노레포**에 **Next.js(App Router) 앱 하나**(`apps/web`)를 두고 경로로 채널을 나눕니다: 고객 `/`, 기사 `/tech`, 관리자 `/admin`. 데이터 변경은 **서버 액션**에서 관리자 권한을 확인한 뒤 처리하고, DB에는 **RLS**를 켜서 브라우저 키로 직접 접근하는 경우도 막습니다. 비즈니스 규칙(견적·상태 전이·정산·코스 최적화)은 프레임워크와 분리된 `packages/domain`에 모아 테스트로 고정합니다. 배포는 **Vercel**, 로그인·DB·파일은 **Supabase**(Auth · PostgreSQL + PostGIS · Storage). 지도는 **카카오맵**, 결제는 **포트원 V2(하부 PG: 토스페이먼츠)**, 알림톡은 **솔라피**를 추천합니다.

## 2. 권장 기술 스택

### 2.1 공통

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어 | **TypeScript** (화면·서버 액션·배치 전부) | Claude Code가 한 언어로 전체 맥락을 잡기 쉽고, 타입이 83개 테이블 간 실수를 줄여줌 |
| 모노레포 | **pnpm workspace + Turborepo** | 웹 앱과 공용 패키지(DB 스키마·도메인 로직·디자인 토큰)를 분리해 테스트·재사용 |
| 검증 스키마 | **Zod** | 폼 검증·API 입력·환경변수 검증을 한 스키마로 |
| 테스트 | **Vitest**(도메인 단위), **Playwright**(단계별 "완료 기준" E2E) | BR 규칙을 테스트로 먼저 고정하면 AI가 고쳐도 깨지지 않음 |
| 린트·포맷 | ESLint + Prettier (또는 Biome) | |

### 2.2 웹 앱 (3채널 = 한 앱의 경로)

| 영역 | 선택 | 비고 |
|---|---|---|
| 프레임워크 | **Next.js 15 (App Router) 앱 1개** `apps/web` | 경로별 루트 레이아웃(route group)으로 `<html data-channel>`을 채널마다 다르게 지정 |
| 경로 | 고객 `/` · 기사 `/tech` · 관리자 `/admin` | 관리자 화면 경로는 `apps/web/src/admin/routes.ts`(화면 ID → 경로) |
| 스타일 | `docs/design-system`의 `tokens.css`·`components.css`를 `packages/ui`로 복사해 그대로 사용(ac- 클래스) | 단계 0은 Tailwind 없이 시작. 도입 시 05 §8.4처럼 CSS 변수 참조 |
| UI 기반 | `packages/ui` React 래퍼(Button·Field·Modal·Toast·Masked·StatusBadge …) | 클래스명·변형 이름은 components.css와 동일 |
| 아이콘 | **Lucide** (`lucide-react`) | 05 §0.2 권고 |
| 폼·검증 | 서버 액션 + **Zod**(`packages/contracts`) | 필수 누락 문구 "○○은(는) 필수 입력값입니다."를 스키마에서 생성 |
| 서버 상태 | 서버 컴포넌트에서 조회, 변경 후 `revalidatePath` | 화면이 복잡해지면 TanStack Query 검토 |
| 관리자 표 | 단계 0은 `.ac-table` 기본 표 | 1만 건 이상 목록(단계 2~)에서 TanStack Table·서버 페이지네이션 |
| 드래그·차트·PWA | dnd-kit · Recharts · serwist + Dexie(IndexedDB) | 해당 단계(4-1, 8, 5)에서 도입 |

### 2.3 서버·데이터

| 영역 | 선택 | 이유 |
|---|---|---|
| 서버 로직 | **Next.js 서버 액션·라우트 핸들러** (별도 API 서버 없음) | Vercel에 한 번에 배포. 외부 웹훅(PG 등)은 `app/api/*` 라우트 핸들러 |
| 권한 | 서버 액션마다 `requirePermission(화면ID, 행위)` → 실패 시 거부. `/admin`은 middleware(세션) + 레이아웃(`requireAdmin`) + 페이지(`requireScreen`) 3중 확인 | RBAC(메뉴×행위) + 거점 범위(BR-102) |
| DB | **Supabase PostgreSQL 16 + PostGIS** (서울 리전) | 관할 구역 포함 판정·거리 계산. PostGIS 확장은 단계 4-2에서 켬 |
| RLS | 모든 테이블 RLS 활성화, `has_permission()`·`can_access_branch()` 정책 | 브라우저에 노출되는 anon/authenticated 키로는 권한 밖 데이터에 접근 불가 |
| ORM | **Drizzle ORM** + drizzle-kit 마이그레이션 | 서버 전용 연결(Supabase Pooler, transaction 모드)로 접근 |
| 인증 | **Supabase Auth** (`@supabase/ssr` 쿠키 세션). 관리자: ID → 이메일·비밀번호, 5회 실패 잠금은 `admin_user`에서 관리 | 고객 소셜 로그인·기사 휴대폰 로그인은 해당 단계(2, 4-1)에서 Supabase Auth 공급자 또는 커스텀 방식으로 확정 |
| 배치 | **Vercel Cron → `/api/jobs/*` 라우트 핸들러** (단계 2 F-SYS-01부터) | 오래 도는 작업이 생기면 Supabase `pg_cron`/큐로 분리 검토. pg-boss는 상시 워커가 필요해 보류 |
| 파일 | **Supabase Storage** (Mock: 로컬 디스크) | `attachment` 메타데이터 + 저장소 어댑터 |
| 실시간 | 초기: 폴링 / 필요 시 Supabase Realtime | 배정 보드·추가요금 동의 대기 |
| 개인정보 | AES-256-GCM 앱 레벨 암호화 + SHA-256 해시 컬럼, 키는 Vercel 환경변수 | ERD §6 |

### 2.4 인프라 (파일럿 기준)

| 구성 | 선택 |
|---|---|
| 웹·서버 | **Vercel** (함수 리전 서울 `icn1`) |
| 인증·DB·파일 | **Supabase** 서울 리전(ap-northeast-2) |
| 모니터링 | Sentry(오류) + 업타임 체크 |

- 개인정보(DB·파일)는 국내 리전에 둡니다. Vercel은 해외 사업자이므로 개인정보처리방침에 **국외 이전·처리위탁 고지**가 필요할 수 있어 법무 확인 항목으로 남깁니다.
- 환경변수: 루트 `.env.example` 참고. `SUPABASE_SERVICE_ROLE_KEY`·`PII_ENCRYPTION_KEY`는 서버 전용(브라우저 번들에 넣지 않음).
- 구현 기간에는 `ADMIN_AUTH_BYPASS=true`로 관리자 화면을 로그인 없이 읽기 전용으로 볼 수 있다(02 §7). 운영 전 Vercel 환경변수에서 지우고 다시 배포한다.

## 3. 프로젝트 구조

```
aircon-life/
├── CLAUDE.md                  ← Claude Code 작업 규칙
├── docs/                      ← 01~06 문서, design-system/ (단일 출처)
├── apps/
│   └── web/                   ← Next.js 앱 하나 (Vercel 배포)
│       └── src/
│           ├── app/(customer)/          고객 웹 `/`        <html data-channel="customer">
│           ├── app/(tech)/tech/         기사 웹앱 `/tech`  data-channel="tech"
│           ├── app/(admin)/admin/       관리자 웹 `/admin` data-channel="admin"
│           │   ├── login/               A-AUTH-010
│           │   └── (protected)/         로그인 필요 영역 (GNB/LNB 레이아웃)
│           ├── admin/                   관리자 공통 UI (셸, 목록형 화면 틀, 화면 ID→경로)
│           ├── server/                  서버 전용: DB 연결, 인증·권한 가드, 감사 로그, 설정값
│           └── middleware.ts            /admin 세션 확인·IP 제한·임시 개발 모드
├── packages/
│   ├── db/                    ← Drizzle 스키마(ERD §2), 마이그레이션(RLS 포함), 시드(common_code·역할·권한·설정)
│   ├── domain/                ← 프레임워크 없는 순수 로직 + Vitest
│   │   ├── rbac/              (메뉴 트리 03 §4.2, 권한 매트릭스 03 §4.4, BR-102 거점 범위)
│   │   ├── auth/              (로그인 잠금, 비밀번호 규칙)
│   │   ├── pricing/           (BR-010 가격 정책 선택 → 단계 1 견적 모듈)
│   │   ├── pii/               (마스킹·암호화·해시)
│   │   └── (단계별 추가) quote/ state-machine/ settlement/ route/ dispatch-rules/
│   ├── contracts/             ← Zod 입력 스키마
│   ├── integrations/          ← 외부 연동 어댑터 (각각 Mock / Real)
│   │   ├── auth/ (Supabase Auth)  storage/ (Supabase Storage)
│   │   └── (단계별 추가) payment/ identity/ notify/ map/ address/ tax/
│   ├── ui/                    ← tokens.css·components.css 복사본 + React 컴포넌트
│   └── config/                ← tsconfig, eslint
└── e2e/                       ← Playwright: 04 구현계획 단계별 완료 기준 시나리오
```

**구조를 이렇게 나눈 이유**

1. **앱 하나 + 경로 분리**: 배포·인증·도메인이 하나라 운영이 단순합니다. 채널별 차이(밀도·레이아웃)는 경로별 루트 레이아웃이 맡고, 관리자 영역은 middleware·레이아웃·서버 액션에서 권한을 확인합니다. Claude Code에게는 "`app/(admin)`만 수정"처럼 경로로 범위를 좁혀 줍니다.
2. **API 서버를 따로 두지 않는 이유**: 상태 전이·정산 규칙은 `packages/domain`에 있으므로 서버 액션·라우트 핸들러가 같은 함수를 호출하면 세 채널이 같은 규칙을 씁니다.
3. **`packages/domain`이 핵심**: 견적·정산·코스 최적화처럼 틀리면 돈과 신뢰가 깨지는 로직을 DB·HTTP와 분리해 테스트로 고정합니다.
4. **`packages/integrations`의 Mock/Real**: 04 원칙 4(모의 → 실연동)를 구조로 강제합니다. 인증도 `AUTH_DRIVER=mock|supabase`로 전환하므로 Supabase 없이 로컬·CI에서 전체 흐름을 돌릴 수 있습니다.
5. **화면 ID = 경로·권한 코드**: 페이지 파일 상단에 화면 ID를 주석으로 달고 `requireScreen('A-…')`·`permission.menu_code`와 일치시킵니다.

## 4. 한국 서비스 연동 비교와 추천

### 4.1 지도·경로 (기사 출동 지도, 관할 구역, 코스 최적화)

| 항목 | **카카오** (추천) | 네이버 클라우드 Maps |
|---|---|---|
| 웹 지도 SDK 무료량 | 일 300,000건 | 월 6,000,000건 |
| 지오코딩(주소→좌표) | 일 100,000건 무료, 초과 0.5원/건 | 월 3,000,000건 무료 |
| 자동차 길찾기 | 카카오모빌리티 내비 API, 일 10,000건 무료 | Directions 5: 월 60,000건 무료 |
| 다중 경유지(코스 경로선) | **일 5,000건 무료** | Directions 15(경유지 15개): **월 3,000건** 무료 |
| 다중 목적지(이동시간 행렬용) | 일 1,000건 무료 | 없음 (Directions 반복 호출) |
| 다각형 그리기(관할 구역 지정) | Drawing 라이브러리 제공 | 직접 구현 |
| 내비 딥링크 | 카카오내비 (+ 티맵·네이버지도 URL 스킴 병행) | 네이버지도 |

**추천: 카카오맵 + 카카오모빌리티 내비 API.** 코스 최적화에 필요한 다중 목적지·다중 경유지 API의 무료량이 파일럿 규모(기사 수명 × 하루 수 회 재계산)에 넉넉하고, 관리자 관할 구역 그리기 도구가 기본 제공됩니다. 주의할 점이 두 가지 있습니다.

- 카카오 지도 무료 쿼터는 개발자 계정에서 **처음 활성화한 앱 1개**에만 주어지고(2026-07-21 정책), 그 외는 비즈월렛 연결 후 유료입니다. 앱 하나에 웹 도메인 3개를 등록해 쓰세요.
- 내비(길찾기) API의 상업적 이용 조건·초과 요금은 공개 문서에 명시돼 있지 않습니다. 실연동 전에 카카오모빌리티 개발자센터에 서비스 용도를 밝히고 확인을 받으세요.

**코스 최적화 구현 방식**
1. 지점 간 이동시간 행렬: 카카오 "다중 목적지 길찾기"를 지점 수만큼 호출해 구성하고 같은 좌표 쌍은 캐시. 실패 시 02 문서대로 직선거리 ÷ 25km/h.
2. 순서 탐색: `packages/domain/route`에서 직접 계산. 10개 이하는 시간창을 고려한 전수/동적계획법, 그 이상은 삽입 휴리스틱 + 2-opt. 하루 5~8건 규모라 외부 최적화 엔진은 필요 없습니다.
3. 확정 코스 경로선: "다중 경유지 길찾기" 1회 호출.

**법정동 경계·주소**
- 주소 검색 UI: **카카오(다음) 우편번호 서비스**(무료, 키 불필요). 결과에 **법정동 코드(bcode)**가 들어 있어 `service_area` 매핑(BR-001)에 바로 씁니다. 정제·검증이 더 필요하면 행정안전부 도로명주소 API 병행.
- 좌표: 카카오 로컬 API 지오코딩.
- 법정동 경계 다각형: 브이월드/국가공간정보포털의 법정동 경계 데이터를 PostGIS로 적재(시드 스크립트).

### 4.2 결제 (앱 결제, 결제 링크, 부분 환불, 현금영수증)

| 항목 | **포트원 V2** (추천, 하부 PG는 토스페이먼츠) | 토스페이먼츠 직접 연동 |
|---|---|---|
| 성격 | 여러 PG를 한 SDK로 묶는 결제 연동 플랫폼 | PG사 직접 연동 |
| 본인인증 | **같은 SDK로 휴대폰 본인인증 제공**(다날·KG이니시스 등) | 별도 업체 필요 |
| 간편결제 추가 | 카카오페이·네이버페이 등을 설정으로 추가 | 토스 결제위젯 안에서 제공 |
| PG 교체·복수 PG | 코드 변경 없이 가능 | 재개발 필요 |
| 문서·개발 경험 | 양호 | 매우 좋음(Claude가 특히 잘 앎) |
| 단점 | 레이어가 하나 더 생김, 장애 지점 증가 | 본인인증·다른 PG는 따로 붙여야 함 |

**추천: 포트원 V2 + 토스페이먼츠 PG 계약.** 이 서비스는 결제와 함께 **휴대폰 본인인증**(F-CUS-AUTH-01, 비회원 견적 → 예약 시 인증)이 필수라 한 번의 연동으로 둘 다 해결되는 점이 큽니다. PG 수수료는 각 PG와 직접 계약 조건에 따르므로 계약 시 확인하세요.

- 현장결제(F-TEC-PAY-01): 파일럿은 **카드 단말기 대신 결제 링크(알림톡/문자)·QR**로 시작하고, 단말기는 필요성이 확인되면 도입을 권합니다.
- 현금·계좌이체 현금영수증: PG의 현금영수증 발행 API 사용.
- 전자세금계산서(B2B, R3): **팝빌** API.
- 정산 지급(F-ADM-STL-04): 초기엔 은행 대량이체 파일 생성(04 단계 7 그대로).

### 4.3 알림 (알림톡 + SMS 대체 + 푸시)

| 항목 | **솔라피** (추천) | NHN Cloud Notification | 알리고 |
|---|---|---|---|
| 알림톡 실패 시 SMS 자동 대체 | 지원 | 지원 | 지원 |
| 개발자 친화성(API·SDK·문서) | 좋음, Node SDK | 좋음, 기능 많음(콘솔 복잡) | 단순·저렴 |
| 템플릿 관리 | 콘솔에서 카카오 검수 요청 | 콘솔 | 콘솔 |

**추천: 솔라피.** 02 문서의 "알림톡 실패 시 SMS 대체"를 옵션 하나로 해결하고 Node SDK가 있어 바이브 코딩에 편합니다. 알림톡은 **카카오 채널 개설 + 템플릿 검수(영업일 수일)**가 필요하니 단계 2 착수 전에 템플릿을 미리 신청하세요.

- 푸시: 웹 푸시(Web Push, VAPID). iOS는 홈 화면에 추가한 PWA에서만 동작(iOS 16.4+)하므로 **고객 알림의 주 채널은 알림톡**, 기사는 PWA 설치 + 웹 푸시로 시작합니다.

### 4.4 소셜 로그인

카카오·네이버는 각 개발자센터에서 OAuth 직접 연동. **애플 로그인은 iOS 네이티브 앱으로 출시할 때 의무**이므로 웹 단계에서는 후순위로 둬도 됩니다.

## 6. Claude Code로 바이브 코딩할 때의 운영 규칙 (CLAUDE.md에 넣을 내용)

1. **문서가 단일 출처**: "테이블은 docs/01_ERD.md §2, 화면은 03_IA, 규칙 BR-xxx는 02 §5를 따른다. 구현 중 바뀌면 문서도 같이 고친다(04 §4 문서 동기화)."
2. **작업 단위 = 04 구현계획의 단계**: 한 세션에 한 단계(단계 5는 5-1/5-2로). 시작할 때 해당 단계 섹션을 통째로 프롬프트에 붙이기.
3. **규칙은 테스트 먼저**: BR 번호마다 정상·예외 테스트를 `packages/domain`에 먼저 쓰고 구현. 테스트 이름에 BR 번호를 넣어 추적.
4. **상태 변경은 한 함수로만**: 모든 상태 변경은 `domain/state-machine`의 전이 함수를 거치고 이력 테이블에 INSERT(ERD 원칙 9).
5. **하드코딩 금지**: 색·반경은 토큰, 금액·시간 기준값(할증 30,000원, 버퍼 10분, 마감 18:00)은 `system_setting`.
6. **외부 연동은 Mock부터**: 실키 없이 전 흐름이 돌아야 다음 단계로.
7. **채널 범위 지정**: 프롬프트에 "apps/web/src/app/(admin) + packages/domain만 수정"처럼 범위를 명시.

4. ✅ `packages/integrations` 인증·저장소 어댑터 (나머지는 해당 단계에서)
5. ✅ CI(GitHub Actions): 타입체크·린트·Vitest·RLS 통합 테스트·E2E
