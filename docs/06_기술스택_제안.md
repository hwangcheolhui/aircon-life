## 0. 한 줄 요약

**TypeScript 하나로 통일한 모노레포**에 프론트 3개(Next.js)와 API 1개(NestJS)를 두고, 비즈니스 규칙(견적·상태 전이·정산·코스 최적화)은 프레임워크와 분리된 `packages/domain`에 모아 테스트로 고정합니다. DB는 **PostgreSQL + PostGIS**, 지도는 **카카오맵**, 결제는 **포트원 V2(하부 PG: 토스페이먼츠)**, 알림톡은 **솔라피**를 추천합니다.

### 2.3 백엔드

| 영역 | 선택 | 이유 |
|---|---|---|
| API 서버 | **NestJS** (REST + OpenAPI 자동 문서) | 모듈·가드·인터셉터 규칙이 정해져 있어 AI가 13개 도메인을 같은 패턴으로 찍어내기 좋음. RBAC 가드, 감사 로그 인터셉터, 크론을 표준 방식으로 처리 |
| DB | **PostgreSQL 16+ + PostGIS** | 관할 구역 포함 판정(`ST_Contains`), 거리 계산, 법정동 경계 저장 |
| ORM | **Drizzle ORM** | SQL에 가까워 ERD 표를 그대로 옮기기 쉽고 PostGIS geometry 타입·마이그레이션 지원. (Prisma도 가능하지만 공간 쿼리는 raw SQL이 많아짐) |
| 잡·큐 | **pg-boss** (Postgres 기반 큐·크론) | Redis 없이 배치 18종 + 알림 재시도 + 사진 후처리. 규모가 커지면 BullMQ+Redis로 교체 |
| 인증 | 자체 구현: 관리자 ID/PW(5회 잠금·IP 제한 옵션), 기사 휴대폰+비밀번호, 고객 카카오·네이버·애플 OAuth + 휴대폰 본인인증. 세션은 httpOnly 쿠키 | 3채널 사용자 테이블이 다르고(admin_user / technician / customer) 규칙이 제각각이라 외부 인증 서비스보다 직접 구현이 단순 |
| 파일 | S3 호환 스토리지(Presigned URL 직접 업로드) | 작업 사진·서명·첨부 |
| 실시간 | 초기: 30초 폴링 / 필요 시 SSE | 배정 보드·추가요금 동의 대기 화면. 웹소켓은 R2 코스 모니터링 때 검토 |
| 개인정보 | AES-256-GCM 앱 레벨 암호화 + SHA-256 해시 컬럼, 키는 클라우드 KMS/시크릿 | ERD §6 |

### 2.4 인프라 (파일럿 기준)

| 구성 | 추천 | 대안 |
|---|---|---|
| DB·스토리지 | **Supabase 서울 리전**(Postgres+PostGIS+Storage, 관리형) | AWS RDS + S3 (서울) |
| API·배치 | 컨테이너 1개, **AWS 서울**(Lightsail 컨테이너 또는 ECS Fargate) | NCP 서버 |
| 프론트 3개 | **Vercel** (함수 리전 서울 icn1 지정) | 같은 AWS에 컨테이너로 |
| 모니터링 | Sentry(오류) + 업타임 체크 | |

- 개인정보(DB·파일)는 국내 리전에 두는 구성입니다. Vercel처럼 해외 사업자를 쓰면 개인정보처리방침에 **국외 이전·처리위탁 고지**가 필요할 수 있어 법무 확인 항목으로 남깁니다.
- 성수기 오토스케일링(02 §7)은 파일럿 이후 ECS로 옮기면서 대응합니다.

## 3. 프로젝트 구조

```
aircon-life/
├── CLAUDE.md                  ← Claude Code 작업 규칙(아래 §6)
├── docs/                      ← 01~06 문서, design-system/ (단일 출처)
├── apps/
│   ├── customer/              ← 고객 웹 (C-*)  <html data-channel="customer">
│   ├── tech/                  ← 기사 웹앱·PWA (T-*)  data-channel="tech"
│   ├── admin/                 ← 관리자 웹 (A-*)  data-channel="admin"
│   └── api/                   ← NestJS API + 배치(jobs 모듈)
│       └── src/modules/
│           ├── auth/  org/(거점·RBAC·코드·설정)  customer/  product/
│           ├── quote/  order/  consult/  technician/
│           ├── dispatch/(슬롯·배정·관할·코스)  work/  payment/
│           ├── settlement/  crm/(알림·캠페인·후기·AS)  content/
│           ├── audit/
│           └── jobs/          ← F-SYS-01~18 (pg-boss 크론)
├── packages/
│   ├── db/                    ← Drizzle 스키마(83 테이블, 도메인별 파일), 마이그레이션, 시드(common_code·공휴일·법정동)
│   ├── domain/                ← 프레임워크 없는 순수 로직 + Vitest
│   │   ├── quote/             (BR-010~015 견적 계산)
│   │   ├── state-machine/     (주문·작업·코스·정산·배정 상태 전이표)
│   │   ├── settlement/        (BR-080~084 배분·상계·원천세)
│   │   ├── route/             (이동시간 행렬 → 최적 순서·ETA, BR-112~114)
│   │   ├── dispatch-rules/    (배정 검증 BR-070~072, 관할 BR-110~111)
│   │   └── pii/               (암호화·해시·마스킹)
│   ├── contracts/             ← Zod DTO + 생성된 API 클라이언트
│   ├── integrations/          ← 외부 연동 어댑터 (각각 Mock / Real)
│   │   ├── payment/ identity/ notify/(알림톡·SMS·웹푸시)
│   │   ├── map/(지오코딩·길찾기·행렬) address/ tax/
│   ├── ui/                    ← tokens.css·components.css + React 컴포넌트(StatusBadge, Masked, BottomBar…)
│   └── config/                ← tsconfig, eslint, tailwind preset
└── e2e/                       ← Playwright: 04 구현계획 단계별 완료 기준 시나리오
```

**구조를 이렇게 나눈 이유**

1. **앱 3개를 분리**: 채널마다 인증 주체·레이아웃·밀도가 다르고, 관리자 웹은 IP 제한·보안 헤더를 따로 걸어야 합니다. Claude Code에게 "apps/tech만 보고 작업해"처럼 범위를 좁혀 줄 수 있어 실수도 줄어듭니다.
2. **API를 따로 둔 이유**: 상태 전이·정산·결제 웹훅·배치는 세 채널이 같은 규칙을 써야 합니다. Next.js 서버 액션에 흩어 두면 같은 규칙이 세 군데 복제됩니다.
3. **`packages/domain`이 핵심**: 견적·정산·코스 최적화처럼 틀리면 돈과 신뢰가 깨지는 로직을 DB·HTTP와 분리해 테스트로 고정합니다. ERD §7의 "§3 상태 정의를 서버 측 상태 전이 검증 로직으로 구현"이 여기에 해당합니다.
4. **`packages/integrations`의 Mock/Real**: 04 원칙 4(모의 → 실연동)를 구조로 강제합니다. 환경변수 하나로 전환합니다.
5. **화면 ID = 라우트·권한 코드**: IA §0.2 원칙 5에 맞춰 페이지 파일 상단에 화면 ID를 주석으로 달고, 권한 가드의 `menu_code`와 일치시킵니다.

## 4. 한국 서비스 연동 비교와 추천

### 4.1 지도·경로 (기사 출동 지도, 관할 구역, 코스 최적화)

| 항목 | **카카오** (추천) | 네이버 클라우드 Maps |
|---|---|---|
| 웹 지도 SDK 무료량 | 일 300,000건 | 월 6,000,000건 |
| 지오코딩(주소→좌표) | 일 100,000건 무료, 초과 0.5원/건 | 월 3,000,000건 무료 |
| 자동차 길찾기 | 카카오모빌리티 내비 API, 일 10,000건 무료 | Directions 5: 월 60,000건 무료 |
| 다중 경유지(코스 경로선) | **일 5,000건 무료** | Directions 15(경유지 15개): **월 3,000건** 무료 |
| 다중 목적지(이동시간 행렬용) | 일 1,000건 무료 | 없음 (Directions 반복 호출) |
| 다각형 그리기(관할 구역 지정) | Drawing 라이브러리 제공 | 직접 구현 |
| 내비 딥링크 | 카카오내비 (+ 티맵·네이버지도 URL 스킴 병행) | 네이버지도 |

**추천: 카카오맵 + 카카오모빌리티 내비 API.** 코스 최적화에 필요한 다중 목적지·다중 경유지 API의 무료량이 파일럿 규모(기사 수명 × 하루 수 회 재계산)에 넉넉하고, 관리자 관할 구역 그리기 도구가 기본 제공됩니다. 주의할 점이 두 가지 있습니다.

- 카카오 지도 무료 쿼터는 개발자 계정에서 **처음 활성화한 앱 1개**에만 주어지고(2026-07-21 정책), 그 외는 비즈월렛 연결 후 유료입니다. 앱 하나에 웹 도메인 3개를 등록해 쓰세요.
- 내비(길찾기) API의 상업적 이용 조건·초과 요금은 공개 문서에 명시돼 있지 않습니다. 실연동 전에 카카오모빌리티 개발자센터에 서비스 용도를 밝히고 확인을 받으세요.

**코스 최적화 구현 방식**
1. 지점 간 이동시간 행렬: 카카오 "다중 목적지 길찾기"를 지점 수만큼 호출해 구성하고 같은 좌표 쌍은 캐시. 실패 시 02 문서대로 직선거리 ÷ 25km/h.
2. 순서 탐색: `packages/domain/route`에서 직접 계산. 10개 이하는 시간창을 고려한 전수/동적계획법, 그 이상은 삽입 휴리스틱 + 2-opt. 하루 5~8건 규모라 외부 최적화 엔진은 필요 없습니다.
3. 확정 코스 경로선: "다중 경유지 길찾기" 1회 호출.

**법정동 경계·주소**
- 주소 검색 UI: **카카오(다음) 우편번호 서비스**(무료, 키 불필요). 결과에 **법정동 코드(bcode)**가 들어 있어 `service_area` 매핑(BR-001)에 바로 씁니다. 정제·검증이 더 필요하면 행정안전부 도로명주소 API 병행.
- 좌표: 카카오 로컬 API 지오코딩.
- 법정동 경계 다각형: 브이월드/국가공간정보포털의 법정동 경계 데이터를 PostGIS로 적재(시드 스크립트).

| 성격 | 여러 PG를 한 SDK로 묶는 결제 연동 플랫폼 | PG사 직접 연동 |
| 본인인증 | **같은 SDK로 휴대폰 본인인증 제공**(다날·KG이니시스 등) | 별도 업체 필요 |
| 간편결제 추가 | 카카오페이·네이버페이 등을 설정으로 추가 | 토스 결제위젯 안에서 제공 |
| PG 교체·복수 PG | 코드 변경 없이 가능 | 재개발 필요 |
| 문서·개발 경험 | 양호 | 매우 좋음(Claude가 특히 잘 앎) |
| 단점 | 레이어가 하나 더 생김, 장애 지점 증가 | 본인인증·다른 PG는 따로 붙여야 함 |

**추천: 포트원 V2 + 토스페이먼츠 PG 계약.** 이 서비스는 결제와 함께 **휴대폰 본인인증**(F-CUS-AUTH-01, 비회원 견적 → 예약 시 인증)이 필수라 한 번의 연동으로 둘 다 해결되는 점이 큽니다. PG 수수료는 각 PG와 직접 계약 조건에 따르므로 계약 시 확인하세요.

- 현장결제(F-TEC-PAY-01): 파일럿은 **카드 단말기 대신 결제 링크(알림톡/문자)·QR**로 시작하고, 단말기는 필요성이 확인되면 도입을 권합니다.
- 현금·계좌이체 현금영수증: PG의 현금영수증 발행 API 사용.
- 전자세금계산서(B2B, R3): **팝빌** API.
- 정산 지급(F-ADM-STL-04): 초기엔 은행 대량이체 파일 생성(04 단계 7 그대로).

### 4.3 알림 (알림톡 + SMS 대체 + 푸시)

| 항목 | **솔라피** (추천) | NHN Cloud Notification | 알리고 |
|---|---|---|---|
| 알림톡 실패 시 SMS 자동 대체 | 지원 | 지원 | 지원 |
| 개발자 친화성(API·SDK·문서) | 좋음, Node SDK | 좋음, 기능 많음(콘솔 복잡) | 단순·저렴 |
| 템플릿 관리 | 콘솔에서 카카오 검수 요청 | 콘솔 | 콘솔 |

**추천: 솔라피.** 02 문서의 "알림톡 실패 시 SMS 대체"를 옵션 하나로 해결하고 Node SDK가 있어 바이브 코딩에 편합니다. 알림톡은 **카카오 채널 개설 + 템플릿 검수(영업일 수일)**가 필요하니 단계 2 착수 전에 템플릿을 미리 신청하세요.

- 푸시: 웹 푸시(Web Push, VAPID). iOS는 홈 화면에 추가한 PWA에서만 동작(iOS 16.4+)하므로 **고객 알림의 주 채널은 알림톡**, 기사는 PWA 설치 + 웹 푸시로 시작합니다.

### 4.4 소셜 로그인

카카오·네이버는 각 개발자센터에서 OAuth 직접 연동. **애플 로그인은 iOS 네이티브 앱으로 출시할 때 의무**이므로 웹 단계에서는 후순위로 둬도 됩니다.

## 6. Claude Code로 바이브 코딩할 때의 운영 규칙 (CLAUDE.md에 넣을 내용)

1. **문서가 단일 출처**: "테이블은 docs/01_ERD.md §2, 화면은 03_IA, 규칙 BR-xxx는 02 §5를 따른다. 구현 중 바뀌면 문서도 같이 고친다(04 §4 문서 동기화)."
2. **작업 단위 = 04 구현계획의 단계**: 한 세션에 한 단계(단계 5는 5-1/5-2로). 시작할 때 해당 단계 섹션을 통째로 프롬프트에 붙이기.
3. **규칙은 테스트 먼저**: BR 번호마다 정상·예외 테스트를 `packages/domain`에 먼저 쓰고 구현. 테스트 이름에 BR 번호를 넣어 추적.
4. **상태 변경은 한 함수로만**: 모든 상태 변경은 `domain/state-machine`의 전이 함수를 거치고 이력 테이블에 INSERT(ERD 원칙 9).
5. **하드코딩 금지**: 색·반경은 토큰, 금액·시간 기준값(할증 30,000원, 버퍼 10분, 마감 18:00)은 `system_setting`.
6. **외부 연동은 Mock부터**: 실키 없이 전 흐름이 돌아야 다음 단계로.
7. **채널 범위 지정**: 프롬프트에 "apps/admin + packages/domain만 수정"처럼 범위를 명시.

## 7. 착수 순서 (04 단계 0 이전의 "단계 −1")

1. 모노레포 뼈대, `packages/ui`에 디자인 토큰 이식, 3개 앱 빈 레이아웃(GNB/LNB, 하단 탭)
